# AI 검사 기회 충전 및 일기 저장 제한 설계

## 목표

사용자에게 제공하는 AI 검사 기회를 일일 3회 전체 초기화 방식에서 최대 2개의 충전식 기회로 변경한다. 매일 오전 9시(한국 표준시)에 기회 1개를 충전하며, 이미 2개를 보유한 경우 추가로 쌓지 않는다. 기기 일기장의 날짜별 저장 한도는 3개에서 2개로 줄인다.

## 확정된 정책

- AI 검사 기회의 최대 보유량은 2개다.
- 신규 사용자와 정책 전환 후 처음 접근하는 기존 사용자는 2개로 시작한다.
- 매일 오전 9시(KST)에 1개를 충전한다.
- 여러 날 접속하지 않았다면 지난 충전 횟수만큼 반영하되 최대 2개까지만 보유한다.
- 2개를 보유한 동안 지나간 충전은 적립하거나 이월하지 않는다.
- 그림 변환과 일기 분석을 묶은 검사 한 번이 기회 1개를 사용한다.
- 기존 정책에서 환불하던 서버 오류는 기회 1개를 반환한다. 콘텐츠 거부 등 기존에 차감을 유지하던 오류는 그대로 유지한다.
- IP 단기 제한과 IP·서비스 일일 비용 보호 제한은 기존 방식을 유지한다. 이 제한들은 사용자에게 지급되는 기회가 아니다.
- 일기 저장은 날짜별 최대 2개다. 저장한 일기를 삭제하면 같은 날짜에 다시 저장할 수 있다.

## 식별 단위

토스 환경에서는 SDK 3.x의 `User.getAnonymousKey()`가 반환하는 `hash`를 클라이언트 식별자의 원천으로 사용한다. Edge Function은 원문을 저장하지 않고 `RATE_LIMIT_SALT`를 포함한 SHA-256 사용자 hash로 변환한다.

일반 브라우저이거나 토스 브리지를 사용할 수 없으면 기존 localStorage 설치 UUID를 사용한다. 이 경우 기회는 토스 계정이 아니라 해당 브라우저 설치 단위로 관리된다.

현재 브랜치에 포함된 `User.getAnonymousKey()` 반환 객체 처리 수정은 이 정책의 선행 조건이다. 이 수정 없이 배포하면 토스 사용자별 충전 지갑이 아니라 WebView 저장소별 충전 지갑이 된다.

## 데이터 모델

사용자 기회 전용 테이블 `diary_ai_user_credits`를 추가한다.

| 필드 | 형식 | 규칙 |
| --- | --- | --- |
| `user_hash` | `text` | 기본 키, 64자리 SHA-256 hex |
| `balance` | `smallint` | `0 <= balance <= 2` |
| `last_refill_slot` | `timestamptz` | 마지막으로 반영한 오전 9시 충전 경계 |
| `created_at` | `timestamptz` | 생성 시각 |
| `updated_at` | `timestamptz` | 마지막 변경 시각 |

RLS를 활성화하고 브라우저 역할의 직접 접근을 금지한다. Edge Function의 service role이 `security definer` RPC를 통해서만 읽고 변경한다.

기존 `diary_ai_rate_limits`는 IP 단기·일일 제한과 서비스 일일 제한에 계속 사용한다. 기존 사용자 일일 `user/all/day` 행은 새 잔여량으로 변환하지 않으며, 전환 후 정리 대상인 과거 기록으로 취급한다.

## 충전 계산

한국 오전 9시는 UTC 00:00이므로 현재 충전 경계는 `date_trunc('day', now())`로 계산한다.

1. 사용자 행이 없으면 `balance = 2`, `last_refill_slot = 현재 경계`로 만든다.
2. 행이 있으면 현재 경계와 `last_refill_slot` 사이의 날짜 수를 계산한다.
3. 경과한 경계가 하나 이상이면 `balance = least(2, balance + 경과 경계 수)`로 갱신한다.
4. 잔여량이 이미 2개여도 `last_refill_slot`은 현재 경계로 전진시킨다. 가득 찬 동안의 충전을 나중에 소급 지급하지 않기 위해서다.

예시:

- 월요일 10시에 0개이면 화요일 09시에 1개가 된다.
- 월요일 10시에 1개이면 화요일 09시에 2개가 된다.
- 월요일 10시에 2개이면 화요일 09시 이후에도 2개다.
- 월요일 10시에 0개이고 목요일 10시에 다시 접속하면 최대치인 2개가 된다.
- 2개인 상태로 여러 날 접속하지 않은 뒤 1개를 사용해도 즉시 과거 충전이 적용되지 않는다. 다음 오전 9시에 다시 1개가 충전된다.

충전은 cron 없이 조회·차감 요청 시 지연 반영한다. 사용자가 접속하지 않을 때 DB를 갱신할 필요가 없고, 사용자가 보는 결과는 실제 오전 9시 충전과 동일하다.

## 원자성과 RPC

새 충전 계약은 기존 일일 사용자 카운터 RPC와 분리된 버전의 RPC로 제공한다. 먼저 새 테이블과 RPC를 배포한 뒤 Edge Function을 전환할 수 있도록 새 이름을 사용한다.

- `consume_diary_ai_inspection_quota_v2`: 충전을 반영하고 잔여량을 확인한 뒤, 허용되면 사용자 기회와 기존 IP·서비스 카운터를 한 트랜잭션에서 차감한다.
- `refund_diary_ai_inspection_quota_v2`: 기존 오류 분류에 따라 사용자 기회를 최대 2개 범위에서 반환하고, 같은 요청이 사용한 IP·서비스 카운터도 기존 정책대로 환불한다.
- `read_diary_ai_inspection_quota_v2`: 사용자 행을 초기화하거나 충전을 반영하고 현재 잔여량과 기존 보호 카운터를 반환한다.

사용자 hash별 advisory lock 또는 잠긴 사용자 행을 사용해 동일 사용자의 병렬 요청을 직렬화한다. 잔여량이 1개일 때 두 요청이 동시에 들어와도 하나만 허용되어야 한다. 기존 서비스 전체 advisory lock이 보호하는 비용 카운터와의 잠금 순서를 모든 RPC에서 동일하게 유지해 교착을 방지한다.

## Edge Function과 응답 계약

Edge Function의 사용자 제한은 `userDaily: 3` 대신 `userCreditCapacity: 2`를 사용한다. IP와 서비스 제한 수치는 변경하지 않는다.

클라이언트에 전달하는 `quota.all` 형식은 호환성을 위해 유지한다.

```json
{
  "all": {
    "used": 1,
    "limit": 2,
    "remaining": 1
  },
  "nextRefillAt": "2026-08-31T00:00:00.000Z"
}
```

`used`는 `2 - balance`로 계산한다. `nextRefillAt`은 다음 UTC 00:00, 즉 다음 KST 오전 9시다.

안전한 순차 배포를 위해 Edge Function은 전환 기간에 `nextRefillAt`과 같은 값을 기존 `resetAt`에도 함께 반환한다. 새 클라이언트는 `nextRefillAt`을 우선 사용하고, 이전 서버와의 호환을 위해 `resetAt`을 대체값으로 허용한다. 모든 클라이언트가 전환된 뒤 `resetAt` 제거 여부를 별도로 결정한다.

## 클라이언트 동작과 문구

- quota snapshot은 `nextRefillAt`을 저장한다.
- 오전 9시가 되면 snapshot 전체를 2개로 가정하지 않고 폐기한 뒤 `quota-status`를 다시 요청한다.
- 충전 경계가 지났다는 이유로 그림 요청 ledger 전체를 초기화하지 않는다. 이미 처리한 같은 사진의 중복 결제를 막는 규칙은 충전 정책과 별개다.
- 화면 문구는 `매일 아침 9시에 1개가 충전돼요. 최대 2개까지 보관할 수 있어요.`로 통일한다.
- 잔여량 소진 안내는 `다음 기회는 아침 9시에 1개 충전돼요.`처럼 전체 초기화를 암시하지 않게 변경한다.
- 서버 상태를 불러오지 못했을 때는 현재 정책대로 잔여량을 임의 생성하지 않고 상태를 숨기며, 서버가 최종 차단 권한을 가진다.

## 일기 저장 한도

`MAX_DIARIES_PER_DATE`를 2로 변경한다. 저장 용량은 계속 기기 `Storage` 또는 브라우저 localStorage에서 관리하므로 서버 충전 테이블과 연결하지 않는다.

- 같은 날짜에 저장된 일기가 2개면 새 저장을 차단한다.
- 같은 날짜의 일기 하나를 삭제하면 다시 하나를 저장할 수 있다.
- 달력의 같은 날짜 일기 순환과 좌우 스와이프는 최대 2개에서도 기존 로직을 그대로 사용한다.
- 저장 성공 토스트와 용량 초과 모달의 분모 및 문구를 2개 기준으로 표시한다.

## 배포 순서

1. 새 사용자 기회 테이블과 v2 RPC를 배포한다. 기존 RPC는 유지한다.
2. `User.getAnonymousKey()` 수정과 v2 RPC를 사용하는 Edge Function을 배포한다.
3. `nextRefillAt`, 2개 한도와 새 안내 문구를 사용하는 웹 번들을 배포한다.
4. AIT Devtools와 QR 환경에서 실제 토스 사용자별 잔여량을 확인한다.
5. 전환 안정화 후 사용하지 않는 기존 사용자 일일 카운터와 RPC의 제거 여부를 결정한다.

저장소의 SQL과 Edge Function 파일은 배포 원본과 일치한다고 보장할 수 없는 스냅샷이므로, 코드 변경만으로 운영 정책이 활성화되지는 않는다. 실제 Supabase SQL 적용과 Edge Function 배포가 필요하다.

## 검증 기준

### 충전 규칙

- 최초 조회는 2개를 반환한다.
- 2개에서 한 번 검사하면 1개, 두 번 검사하면 0개가 된다.
- 0개에서 추가 검사는 유료 외부 API를 호출하기 전에 거부된다.
- 다음 오전 9시 경계가 지나면 0개는 1개, 1개는 2개, 2개는 2개가 된다.
- 여러 날 미접속해도 2개를 초과하지 않는다.
- 잔여 1개에서 두 병렬 검사 요청 중 정확히 하나만 허용된다.
- 환불 대상 오류는 잔여량을 1개 돌려주되 2개를 초과하지 않는다.
- 차감 유지 대상 오류는 잔여량을 돌려주지 않는다.

### 식별 및 보호 제한

- 같은 토스 익명 hash를 사용하는 재실행·다른 기기 요청이 같은 잔여량을 본다.
- 서로 다른 토스 익명 hash는 독립된 잔여량을 본다.
- 일반 브라우저는 설치 UUID별로 독립된 잔여량을 본다.
- IP 단기 제한과 IP·서비스 일일 제한은 기존 경계에서 계속 동작한다.

### 클라이언트와 저장

- 오전 9시가 지난 열린 세션은 서버를 다시 조회해 1개 충전을 반영한다.
- 잔여량 UI가 `0/2`, `1/2`, `2/2` 범위 밖의 값을 표시하지 않는다.
- 날짜별 세 번째 일기 저장은 차단되고, 하나를 삭제한 뒤에는 저장할 수 있다.
- lint, TypeScript 검사와 Vite·AIT 프로덕션 빌드가 통과한다.

## 범위 밖

- 충전 기회 구매·광고 보상·관리자 수동 지급
- 사용자의 충전 이력 화면
- IP·서비스 비용 보호 제한의 수치 변경
- 기기 일기 원본의 서버 동기화
- 기존 사용자 일일 사용 횟수를 새 잔여량으로 변환하는 마이그레이션
